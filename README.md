# 城市天气与空气质量数据平台

以 [Open-Meteo](https://open-meteo.com/) 为数据源，围绕同一份数据湖提供**两个职责分离的服务**，
前端合并为**一个入口、顶栏一键切换**：

| 平台 | 面向 | 默认端口 | 回答什么问题 | 页面 |
| --- | --- | --- | --- | --- |
| **分析平台** | 业务分析人员 | 8000 | 数据说明了什么？污染过程怎么发生的？达标了吗？ | 11 个 |
| **治理平台** | 数据治理部门 | 8001 | 这份数据归谁管？字段什么含义？从哪来到哪去？质量如何？ | 5 个 |

打开任一地址都是**同一套前端**：顶栏 `分析平台 / 数据治理` 分段开关一键整站切换，
侧边栏与内容区随之一并切换。两个服务各自注入 `/portal-config.js`，告诉前端
「我是谁」与「另一个在哪」，因此：

* 收藏 **8000** → 默认落在分析平台；收藏 **8001** → 默认落在治理平台；
* 两个服务仍可**分别部署到不同机器**（配置 `ATMOS_ANALYSIS_PUBLIC_URL` /
  `ATMOS_GOVERNANCE_PUBLIC_URL`），而前端代码只有一份。

职责边界由测试兜底：两个平台的接口集合除 4 个框架接口外互不重叠，
调错门户会得到 404 并提示"请确认请求发往了正确的端口"。

```
Open-Meteo API
      │  ① 采集（限流 + 重试 + 契约校验）
      ▼
 Parquet 数据湖（分区存储）  ←── ② 派生：天气 ⨿ 空气质量 → 融合宽表 → 日汇总
      │  ③ DuckDB 直接读 Parquet
      ├──────────────────────────────┐
      ▼                              ▼
 分析平台 API（33 个操作）      治理平台 API（28 个操作）
      └──────────────┬───────────────┘
                     ▼
     统一前端（16 个页面，顶栏一键切换）

 横切：SQLite 资产目录 = 元数据 / 字段字典 / 血缘 / 质量 / 运行记录
```

## 快速开始

### 环境要求

Python **3.11+**（验证于 3.12）。无需数据库服务、无需 API Key、无需前端构建。

### 安装

```bash
python -m venv .venv
```

**激活虚拟环境（可选）** —— Windows PowerShell 默认执行策略会阻止 `Activate.ps1`：

```powershell
# 推荐：直接用 venv 中的解释器，绕开执行策略
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"

# 或改用 cmd.exe（activate.bat 不受 PowerShell 策略限制）
.venv\Scripts\activate.bat
```

```bash
# macOS / Linux
source .venv/bin/activate && pip install -e ".[dev]"
```

### 启动

```bash
python -m atmos init                    # 建表 → 引导 → 采集 → 质量评测
python -m atmos serve --portal both     # 同时启动两个平台
```

未激活虚拟环境时把 `python` 换成 `.\.venv\Scripts\python.exe`。

**启动后会自动用默认浏览器打开看板**，不需要手动复制地址。
实现上不是"启动后等几秒"，而是轮询 `/api/health`，**探测到服务真正可响应再打开** ——
机器快慢不一，固定延时要么打开一个连接被拒的页面，要么纯粹干等。
探测超时（默认 30 秒）后仍会打开，因为地址是对的，比静默什么都不发生更有用。

不用自动打开时加 `--no-open`，或设 `ATMOS_OPEN_BROWSER=false`（服务器与 CI 建议关闭）。
然后打开 <http://127.0.0.1:8000/>（分析）与 <http://127.0.0.1:8001/>（治理）。

### Windows 快捷脚本

| 脚本 | 作用 |
| --- | --- |
| `start.cmd` | 双击启动两个平台（可接参数：`start.cmd --portal analysis`） |
| `stop.cmd` | 结束服务并释放端口 |

> 两个脚本刻意保持 **纯 ASCII**：cmd.exe 按 OEM 代码页（中文 Windows 为 GBK）读取 `.cmd`，
> 若文件里写 UTF-8 中文，字节序列会破坏命令解析。中文输出全部由 Python 进程打印。

### 分开部署

```bash
python -m atmos serve --portal analysis                  # 只起分析平台（8000）
python -m atmos serve --portal governance                # 只起治理平台（8001）
python -m atmos serve --portal both --port 8100 --governance-port 8101
```

只起一个服务时统一前端仍然可用 —— 另一个平台的页签会提示该后端未启动，
当前平台的功能不受影响。

两个服务可以部署到不同机器，只要指向同一份 `ATMOS_LAKE_DIR` 与 `ATMOS_CATALOG_DB`，
并配置 `ATMOS_ANALYSIS_PUBLIC_URL` / `ATMOS_GOVERNANCE_PUBLIC_URL` 让浏览器能找到对方，
同时把 CORS 允许来源从 `*` 收紧为前端实际来源。生产环境建议分析平台只读挂载数据湖，
采集与目录写入交给治理侧。

### 验证运行状态

服务起来后可以跑一遍端到端自检，它会验证两个平台的健康、职责边界、
以及六大分析能力在真实数据上给出的结论：

```bash
.\.venv\Scripts\python.exe verify_platform.py
```

想确认前端拿到的是哪个门户、两个后端地址是否正确，直接看注入脚本：

```bash
curl http://127.0.0.1:8000/portal-config.js   # current=analysis
curl http://127.0.0.1:8001/portal-config.js   # current=governance
```

> **数据不会自动更新**：内置定时调度尚未实现（配置项已预留）。刷新数据用
> `python -m atmos collect`，或在分析看板的「数据刷新」页点一次采集。

## 分析平台

### 基础数据服务

实时实况（含空气质量等级、首要污染物、健康提示与阈值预警）、逐小时 / 逐日时序
（带实况与预报分界线）、多城市同指标对比、空气质量排名、基于 ERA5 的长期趋势。

### 六大类深度分析

> **AQI 口径**：合规考核一律使用**国标 AQI（GB 3095-2012 / HJ 633-2012）** ——
> PM 用 24 小时滑动平均、O₃ 用 8 小时滑动平均计算 IAQI，AQI ≤ 100 为优良。
> 欧洲 AQI（EAQI）与国际对比并存但**不用于考核**：两者刻度差异极大
> （EAQI 的"良"上界 40 大致对应 PM2.5 20 μg/m³，国标 AQI 100 对应 75 μg/m³），
> 混用会让国内城市的优良率被严重低估（实测同一批数据：9% vs 64%）。

| # | 分析 | 回答的问题 | 关键输出 |
| --- | --- | --- | --- |
| 1 | **统计与分布** | 数据长什么样？离群点在哪？ | 分位数 P5/P25/P50/P75/P95、箱线图五数概括、直方图分箱、Pearson + Spearman 相关矩阵 |
| 2 | **时段规律画像** | 一天里什么时候最脏？工作日和周末有差别吗？ | 城市 × 小时热力图、峰值/谷值时段与日内振幅、工作日 vs 周末对比、月度趋势 |
| 3 | **异常与污染过程** | 共有几次污染过程？从何时开始、持续多久、峰值多少、成因是什么？ | 异常点（Z 分数 / Tukey 围栏）、污染过程清单（起止时间、持续时长、峰值等级、首要污染物、期间风速/湿度/降水/静稳小时、严重度），并自动区分**单次过程**与**持续性污染** |
| 4 | **归因分析** | 为什么这次污染重？ | 散点图、Pearson/Spearman 系数、分箱均值曲线、一元回归（斜率 / R²）、自动生成的结论句与"相关≠因果"提示 |
| 5 | **达标考核与报表** | 优良天比例达标了吗？哪些城市拖后腿？和上期比是改善还是转差？ | 逐城市优良天比例与目标完成度、国标等级天数分布、超标天/小时、环比、同比、一键导出 CSV |
| 6 | **横向对比** | 哪些城市环境特征接近？能归为同一类管理吗？ | KMeans 聚类分组与自动命名、相似度矩阵、最相似城市对、轮廓系数选 K |

### 页面（11 个）

路由统一带门户前缀（`#/analysis/...`），与治理平台的页面互不冲突：

| 路由 | 页面 | 内容 |
| --- | --- | --- |

## 治理平台

刻意精简为**三块核心能力 + 运行审计**，不包含数据刷新触发与环境数据查询，
使治理部门的职责边界不与环境分析工作重叠。

### 1. 资产目录

- **治理元数据**：责任人（owner）、数据管理员（steward）、SLA 新鲜度与完整度要求、
  更新频率、分层（参考层 / 原始层 / 精炼层 / 服务层）、敏感级别、来源与许可
- **字段字典（171 个字段）**：类型、单位、业务含义、值域约束、枚举集合、是否主键、是否派生
  —— 它同时是质量引擎的校验输入
- **版本快照**：每次落湖的分区统计与体积变化
- **数据预览**：样例数据与列级画像（空值率、唯一值数、极值、越界计数）

### 2. 数据血缘

- 从数据源原始端点，经采集作业与关联变换，到对外服务层数据集的完整有向图（7 节点 8 边）
- **影响分析**（这个资产坏了会影响谁）与**根因追溯**（这张表脏了问题出在哪）
- 血缘孤岛巡检：找出未接入血缘或缺少转换说明的资产

### 3. 质量评分

- **五维模型**：完整性 0.28 / 时效性 0.20 / 有效性 0.24 / 一致性 0.18 / 唯一性 0.10
- **14 项检查**，按严重级别（严重 3 / 重要 2 / 次要 1）加权合成维度分，再合成总分，映射 A–E 等级
- **逐项明细**：观测值、阈值、违规样本、影响记录数

### 运维审计

作业清单、数据源字段契约、逐条运行记录（行数、字节、API 调用、去重数、schema 漂移、错误）、
元数据同步与统计刷新。**不包含触发采集** —— 那是分析平台"刷新数据"的职责。

### 页面（5 个）

| 路由 | 页面 | 内容 |
| --- | --- | --- |
| `#/governance/overview` | 资产总览 | 资产/字段数、质量等级分布、五维雷达、SLA 超期清单 |
| `#/governance/assets` | 资产目录 | 资产卡片与筛选、详情抽屉（字段字典 / 版本 / 检查项 / 样例 / 列级画像） |
| `#/governance/lineage` | 数据血缘 | 分层血缘图、影响分析面板 |
| `#/governance/quality` | 数据质量 | 五维评分、等级分布、逐项检查明细、触发评测 |
| `#/governance/ops` | 运行审计 | 作业清单、运行记录、元数据同步与统计刷新 |

## 统一入口与门户切换

前端只有**一份代码**（`web/app`），8000 与 8001 两个服务托管同一套资源，
差别只在运行时注入的 `/portal-config.js`：

```js
window.__ATMOS_PORTALS__ = {
  current: "analysis",                                  // 本服务是谁
  endpoints: { analysis: "http://127.0.0.1:8000",       // 两个后端在哪
               governance: "http://127.0.0.1:8001" }
}
```

由此得到的行为：

| 行为 | 说明 |
| --- | --- |
| **一键切换** | 顶栏 `分析平台 / 数据治理` 分段开关，一次点击整站切换侧边栏与内容区，不刷新页面 |
| **落地页自适应** | 收藏 8000 默认进分析平台，收藏 8001 默认进治理平台（读注入的 `current`） |
| **记位置** | 切换前记住各平台停留的页面，切回来仍在原处（`localStorage`） |
| **路由加前缀** | `#/analysis/ops` 与 `#/governance/ops` 是两个不同页面 —— 两个平台都有 `ops`，不加前缀必然冲突 |
| **降级** | 另一个后端没启动时，该平台页签给出「治理平台未启动，请运行 start.cmd」提示，当前平台功能不受影响 |
| **边界不放宽** | 前端能同时访问两个后端，但**服务端**边界不变：分析平台仍然不提供 `/api/assets`（404） |

前端目录：

```
web/app/            index.html + static/portal.config.js + static/views/（16 个视图）
web/shared/         api.js 按门户选后端地址；portal.js 负责切换与路由；theme.js 深浅状态/强调色/图表配色的唯一来源；charts/ui/tasks/style
```

其中分析平台的 `refresh.js`（数据刷新）与治理平台的 `audit.js`（运行审计）
原本都叫 `ops`，合并时必须区分文件与路由 —— 现在按用途命名，避免看起来像同一个页面。

### 外观：深浅状态 + 强调色

顶栏有两个控件，两者**正交**，可任意组合：

| 控件 | 取值 | 记忆键 |
| --- | --- | --- |
| **深浅状态** | 深色（默认）/ 浅色 | `localStorage['atmos.mode']` |
| **强调色** | 科技蓝（默认）、湖青、紫罗兰、翠绿、琥珀、玫红 | `localStorage['atmos.theme']` |

两者都是全局偏好（两个门户共用），切换后当前视图会重画 —— 图表颜色是渲染时取出来的，
不重画就会出现"面板变白了、图表还是深色轴"的错配。

#### 单一来源：`web/shared/theme.js`

界面颜色有两条消费路径 —— 样式表（CSS 变量）与图表（ECharts 的 `option`）。
若各维护一套取值，换肤必然漏掉一边。因此令牌只写在 `theme.js`：

- `MODES.dark` / `MODES.light`：结构色与语义色（约 60 个令牌，**两侧键必须一致**）；
- `THEMES`：每个强调色**只声明一个主色**，其余由它推导；
- `applyMode()` / `applyTheme()` 把令牌写到 `:root` 的 CSS 变量上；
- 图表侧用 `ink()`（中性色）与 `seriesPalette()`（序列配色）读**同一份内存副本** ——
  不读 DOM，因此在没有 DOM 的 Node 环境里也能求值，测试才跑得起来。

强调色的推导规则：

| 令牌 | 推导方式 | 用途 |
| --- | --- | --- |
| `--accent` | 主题主色 | 按钮、导航高亮、选中边框 |
| `--accent-hover` | 主色暗 12% | 悬停态 |
| `--accent-soft` | 主色 14% 透明 | 选中底纹、柔和高亮 |
| `--accent-faint` | 主色 6% 透明 | 表格行悬停 |
| `--accent-ink` | **深色态**向白混 55%；**浅色态**暗 28% | 柔和底纹上的文字 |
| `--series-1..10` | 主色打头 + 固定分类色 | 图表序列配色 |

`--accent-ink` 必须按状态朝相反方向推导：深色底上要浅色调、白底上要深色调。
两边同向就会有一边不可读 —— 这正是浅色主题最容易犯的错（见"踩过的坑"第 16 条）。

样式表的 `:root` 保留一套等于 `MODES.dark` 的取值，作用只是**脚本执行前的首屏**
不闪色；它由 `MODES.dark` 生成而非手抄，测试里有逐项断言防止漂移。

#### 有意不随主题变化的颜色

评级 A–E、空气质量分级、达标/告警、血缘分层的**底色**，以及城市/聚类这类分类色：
它们承载含义或用于区分实体，必须在任何主题下保持稳定，因此在各自视图里硬编码是
有意为之。会变的是这些语义色对应的**文字色**（`--ok-ink` 等）与图表中性色 ——
为深色底挑的浅色文字直接放到白底上不可读，这类必须换。

#### 可读性有测试兜底

浅色主题最容易出"浅底浅字"这种只有肉眼能发现的问题，因此
`test_frontend_theme.py` 按 WCAG 相对亮度把关键组合逐对算了一遍
（正文、次要文字、强调色文字、五种语义色文字，各在两种状态下），
徽标这类"语义色 14% 透明叠在面板上"的组合会先合成再计算，避免高估。

## 可选城市与数据资产

**15 个国内大城市**（4 个直辖市、10 个省会、1 个计划单列市）：
北京 上海 广州 深圳 成都 重庆 杭州 南京 武汉 西安 天津 沈阳 乌鲁木齐 拉萨 海口

城市主数据的增删只改 `config/cities.yaml`：`bootstrap` 会把配置幂等投影到资产目录 ——
新增城市自动注册；**移除的城市被停用而非删除**（历史运行、质量结果与数据湖分区仍引用该城市，
硬删除会破坏引用完整性），重新加入配置即自动恢复启用。

| 资产 Key | 名称 | 分层 | 粒度 | SLA |

| `openmeteo.geocoding.places` | 城市地理编码参考数据 | 参考层 | 城市 | 7 天 |
| `openmeteo.weather.forecast.hourly` | 逐小时天气数据 | 原始层 | 逐小时 | 120 分钟 |
| `openmeteo.weather.forecast.daily` | 逐日天气数据 | 原始层 | 逐日 | 24 小时 |

| `openmeteo.air_quality.hourly` | 逐小时空气质量 | 原始层 | 逐小时 | 180 分钟 |

**分析深度取决于数据历史**：空气质量按数据源上限回补 **92 天**，ERA5 归档回补 **180 天**。

## 技术选型：为什么

| 选了 | 没用 | 理由 |
| --- | --- | --- |
| **Parquet 存数据** | MySQL | 时序分析是列式扫描，列存比行存快一个数量级；Parquet 文件本身即可移植资产 |
| **SQLite 存元数据** | PostgreSQL | 元数据量小但需事务与外键；零部署，符合"一键启动" |
| **DuckDB 查询** | 把数据灌进 SQLite | 直接读 Parquet，无需 ETL 搬运；进程内运行，不引入服务 |
| **numpy 自实现统计与 KMeans** | scikit-learn / scipy | 所需算法都是教科书级的，自实现合计不到 300 行；引入两者会让依赖增加约 60MB，与"一键启动"冲突。自实现还便于控制空值、常量序列、样本不足等边界并加以测试 |
| **配置即代码（YAML）** | 元数据存表 | YAML 能进 Git，可 review、可 diff："谁什么时候把 SLA 从 120 分钟改成 180 分钟"在 git log 里有据可查 |
| **一个代码库两个服务** | 两个独立仓库 | 共享核心（取数、口径、写入、质量）只有一份实现，不会在两个部门之间分叉；同时各自可独立部署与演进 |
| **前端不用框架** | Vue/React | 去掉构建步骤，克隆完就能跑；代价是手写 DOM，所以额外写了端点契约测试防回归 |

## 分析引擎的实现要点

**1. 取数口径集中在一处。** 所有分析器都通过 `FrameLoader` 拿数据，城市过滤、时间窗口、
空值清洗只定义一次。否则"每个分析器各写一套清洗"迟早导致同一指标在不同页面数值不一致。

**2. 数据不足返回可读说明而不是报错。** 每项分析的响应都带 `available` 字段；
无数据时返回 `available: false` 与中文 `message`，前端据此展示"先去采集"引导。
这让空库首次启动的体验是"有指引"而不是"一片红"。

**3. 污染过程识别做了"间隙合并"。** 两次超标之间若间隔不超过 3 个达标小时，视为同一次过程。
不做合并的话，一次持续两天的污染过程会因为中间某个小时的短暂好转被切成十几段，
失去"过程"的业务意义。

**4. KMeans 用 KMeans++ 初始化 + 多次重启。** 单次随机初始化容易陷入局部最优，
导致同一批数据两次跑出不同分组。多次重启取 inertia 最小者，并固定随机种子保证结果可复现。
聚类前必须做标准化 —— 否则气压（≈1000）会完全主导距离，风速（≈10）形同不存在。

**5. 相关性同时给 Pearson 与 Spearman。** 两者差异本身是信息：
若秩相关明显强于线性相关，说明关系是单调但非线性的（例如"风速越大 PM2.5 越低，但边际效应递减"）。
页面上同时标注"相关不等于因果"。

**6. 时区正确性。** 数据时间戳是城市本地时间，审计时间是 UTC。数据新鲜度按各城市本地时间计算；
预报表含未来时段，新鲜度只看"本应已到达"的部分。这两处都踩过坑，见下节。

## 设计取舍

**1. 为什么"数据不足"不报错。** 分析平台可能在空库状态下被打开。每项分析返回
`available: false` + 中文说明，前端渲染成带跳转按钮的空状态。这比 500 更有用。

**2. 为什么治理体检被移除。** 原平台有 8 条治理线的自动化体检。实践中它更接近
"一次性评估"而非日常工具，与资产目录、血缘、质量三块高频能力相比价值密度低，
因此从治理平台移除，相关数据并入总览。治理平台因此只有 5 个页面。

**3. 为什么触发采集只放在分析平台。** 数据刷新是分析人员的日常动作（"我要最新数据"），
而治理部门关心的是"数据是怎么进来的、有没有出问题"。让两个平台都能写数据会导致
责任边界模糊，因此治理平台只读运行记录。

**4. 派生作业覆盖上游而非追加。** 每日重算近 7 天窗口的融合宽表与日汇总，而不是只算增量。
原因是空气质量数据在预报期内会被上游反复修正，只追加会留下过时版本。
写入器的幂等去重让"重算"和"追加"在代码上无差别。

**5. 缺失维度从质量分母剔除而不是记零分。** 若某维度下所有检查都被跳过，
该维度从总分分母中剔除并重新归一化权重，避免"资产只声明三个维度就必然低分"的错误结论。

## 踩过并修掉的坑

这些都是"看起来正常但结论错误"的类型，也是最能体现工程判断的部分：

| # | 问题 | 修正 |
| --- | --- | --- |
| 1 | **时区**：数据是城市本地时间，审计是 UTC，直接相减导致所有城市新鲜度系统性偏差数小时 | 按各城市本地当前时间分别计算 |
| 2 | **预报表的"负延迟"**：取 `max(time)` 会取到 7 天后的预报值，报出"延迟 -8757 分钟" | 新鲜度只看"本应已到达"的时段 |
| 3 | **ERA5 发布延迟被当成数据缺失**：归档滞后 5 天，完整性检查给 84 分 C 级 | 给每个资产声明覆盖率窗口的锚点偏移（归档前移、预报后移），修复后 A 级 |
| 4 | **日粒度被小时精度误判**：日汇总时间戳是当日零点，"今天"这行在 21 点时被算作尚未开始 | 日粒度对齐到当日零点 |
| 5 | **空值率被稀释**：按全部单元格聚合时，一个必需字段整列为空只有 2.9% 空值率、仍判"通过" | 改为逐列评分，整列为空即 0 分 |
| 6 | **分级预警重复**：AQI 124 同时命中"重度污染"与"严重污染"，一个城市报 3 条 | 同一指标只报最严重的一条，10 条噪声降到 4 条 |
| 7 | **循环导入**：`lake.writer` ←→ `catalog` 互相依赖 | 用 `TYPE_CHECKING` 打破运行时依赖 |
| 8 | **日汇总列名映射**：用小时指标名查日表会静默查空（`european_aqi` 在日表里叫 `aqi_avg`） | 建立显式别名映射表 |
| 9 | **`.cmd` 脚本编码**：UTF-8 中文被 cmd 按 GBK 读取，破坏引号解析 | 脚本保持纯 ASCII |
| 10 | **未注册 API 返回 405**：请求落到静态文件处理器 | 挂载静态资源前注册 `/api/*` 兜底返回 404 JSON |
| 11 | **AQI 口径用错标准**：用欧洲 AQI ≤ 40 判"优良天"，同一批数据只有 9% 优良率，国标口径下是 64% | 实现 GB 3095-2012 国标 AQI（PM 走 24 小时滑动平均、O₃ 走 8 小时滑动平均），考核一律用国标，EAQI 仅作国际对比 |
| 12 | **融合宽表九成气象列为空**：天气只覆盖 9 天、空气质量覆盖 99 天，外连接后大部分行没有风速与降水，归因分析样本被压缩到十分之一 | 把 ERA5 归档作为历史气象来源补进融合宽表（预报优先、归档兜底），并把这条上游正式写入血缘 |
| 13 | **CSV 导出把中文报表名放进 HTTP 头**：HTTP 头只能是 latin-1，Starlette 抛 `UnicodeEncodeError` 变成 500 | 报表名按 RFC 3986 百分号编码，并加测试断言所有响应头都能 latin-1 编码 |
| 14 | **一个括号写错、整个视图打不开**：数组字面量用 `)` 收尾，浏览器报 `Unexpected token ')'`。而 `node --check` 对它**假通过**（同一个坏文件存成 `.mjs` 退出码 1、存成 `.js` 退出码 0），静态契约测试也不解析源码，于是 272 项测试全绿 | 修正括号；新增 `test_frontend_syntax.py` 用 V8 解析器逐文件校验（已用"故意改回错误"验证过它确实会红） |
| 15 | **"修好了但页面还报旧错"**：静态资源不发 `Cache-Control`，浏览器按 RFC 9111 启发式规则复用旧模块，而动态 `import()` 不吃强制刷新 | 给 `/shared`、`/static` 与 `index.html` 统一加 `no-cache`（仍缓存，但每次先带 ETag 校验），并加断言 |

## 已知边界与后续演进

**当前边界（诚实说明）**

- **无定时调度**：配置项已预留，但需要手动触发采集
- **无鉴权**：没有用户体系，接口全开放；生产环境需加认证与资产级权限
- **浅色状态不跟随系统**：深浅是手动选择并记忆的，没有读取
  `prefers-color-scheme`。跟随系统需要引入"跟随 / 强制深 / 强制浅"三态，
  是另一个交互决定，这一版不做
- **预警只算不推**：阈值规则能正确触发，但没有 Webhook / 邮件推送
- **不适合超大数据**：质量评测把整表读进 pandas 计算，适合中小规模；
  上量需改为 DuckDB 下推聚合 + 按城市分批 + 增量评测
- **SQLite 单写者**：两个平台同时启动时靠 `busy_timeout` 串行化，元数据写入量大时需换 PostgreSQL
- **同比受限于归档长度**：默认回补 180 天，同比需要约 400 天，页面会明确提示而不是给出错误结论

**后续演进**

- [ ] 内置 cron 调度（配置项已预留）
- [ ] 预警推送：Webhook / 邮件
- [ ] 分析报告订阅：定期生成 PDF/Excel 并推送
- [ ] 更多分析：污染过程溯源（后向轨迹）、区域传输贡献拆分、排放源反演
- [ ] 资产订阅与审批：数据使用申请、授权与审计日志
- [ ] 时序压缩：归档层按年合并分区、ZSTD 字典调优
